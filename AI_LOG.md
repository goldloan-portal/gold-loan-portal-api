### GLA-11 — POST /api/v1/leads/submit

- Prompt: "Work on the story GLA-11 using the workflow and the worktree." The Jira ticket body (fetched via the Atlassian MCP) specified Zod validation, purity/LTV calculation, 7-day mobile-number deduplication, and Prisma `Lead` persistence as one unit, explicitly covering `GLA-12`–`GLA-15`.
- Key decisions: installed Zod now that a ticket actually needs it (previously documented as "coming soon"), using its v4 top-level APIs (`z.uuid()`, array-form `z.literal([18, 22, 24])`) rather than the older chained equivalents. The ticket grouped `netWeightGrams <= grossWeightGrams` under "Zod validation," but this repo's own `validation.md` classifies cross-field conditions as business logic — implemented it as a service-layer guard (`ensureNetWeightNotExceedingGross`, 400) instead of a Zod `.refine()`, and likewise checked `selectedPlanId` against the database in the service (`ensureLoanSchemeExists`, 404) rather than the schema. `purityKarat` modeled as a real Prisma enum (`GoldPurity`) per this repo's "fixed set of values → Prisma enum" rule, with a pure `toGoldPurity` mapper in `lead.util.ts` converting the validated `18 | 22 | 24` literal for persistence — the pure gold weight formula itself still multiplies by the raw karat number, not the enum. `MAX_LTV_RATIO` (0.75) and `GOLD_RATE_PER_GRAM` (a placeholder `6500`, no live rate feed exists) are hardcoded constants in `src/config/gold-loan.config.ts`, matching the ticket's literal formula and the assignment brief's framing of 75% as a single global RBI ceiling — deliberately not read from `LoanScheme.maxLtv`, even though that field exists and is currently `75.0` for both seeded plans, since the ticket didn't ask for per-scheme LTV differentiation; worth revisiting if that becomes a real requirement. Added a new `ValidationError` (400, carries field-level `details`) alongside `DuplicateLeadError` (409) and `LoanSchemeNotFoundError` (404), all following the existing `AppError` subclass convention; the error-handler middleware checks `ValidationError` before the generic `AppError` branch so its `details` array reaches the client. Verified the exact assignment example (45g net @ 22K) against the live Supabase database end-to-end via `curl` — `pureGoldWeight` `41.25`, `maxEligibleLoan` `201093.75` — plus all four error paths (dedup, net>gross, bad mobile regex, unknown plan), then deleted the test row afterward.

### GLA-21 — POST /api/v1/leads/calculate

- Prompt: "Work on GLA-21" — the Jira ticket body (Step 2: Dynamic Loan Calculator & Scheme Selection, explicitly covering GLA-22 + GLA-23) called for a backend preview endpoint the frontend calls as gross/net/purity inputs change, computing pure gold weight and max eligible loan server-side so the frontend never duplicates the financial math — plus the frontend consuming `GET /api/v1/loan-schemes` for plan-selection cards, which already existed from GLA-8.
- Key decisions: reused `calculatePureGoldWeight`/`calculateMaxEligibleLoan` from `lead.util.ts` and the same `GOLD_RATE_PER_GRAM`/`MAX_LTV_RATIO` constants `createLead` already uses, rather than introducing parallel logic — the ticket's "single source of truth for financial math" AC applies as much within this repo as to the frontend. `calculateLeadSchema` factors the three shared fields (`grossWeightGrams`, `netWeightGrams`, `purityKarat`) out of `createLeadSchema` into a shared object literal instead of duplicating them, so the two schemas can't drift. `selectedPlanId` deliberately excluded from the calculate payload: `maxEligibleLoan` is derived from the fixed 75% `MAX_LTV_RATIO` config constant, not `LoanScheme.maxLtv`, so plan selection doesn't affect the calculation (confirmed by reading `createLead`'s existing logic before assuming). Since the endpoint does no I/O (no DB read/write — it's a stateless computation validated and returned directly), both `leadService.calculateLead` and the controller's `calculateLead` are plain synchronous functions rather than `async`, unlike every other function in these files; Express 5 still forwards a synchronous throw (e.g. the net-vs-gross `ValidationError`) to the error middleware without needing an `async`/`await` wrapper. Placed `calculateLead` under `// READS` in the service (non-mutating, no different from a computed get) but under `// WRITES` in the controller/route (this repo's controller convention keys off HTTP method, and it's a `POST`). Verified end-to-end via `curl` against the assignment's worked example (45g net @ 22K → `pureGoldWeight: 41.25`, `maxEligibleLoan: 201093.75`), plus the net>gross and bad-purity error paths, and confirmed `GET /api/v1/loan-schemes` still returns the two seeded plans unchanged.
- Files: `src/schemas/lead.schema.ts`, `src/types/lead.types.ts`, `src/services/lead.service.ts`, `src/controllers/lead.controller.ts`, `src/routes/lead.routes.ts`, `CHANGELOG.md`.
